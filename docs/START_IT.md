# Радар: инструкция для IT

Поставка: **2026.11.05-handover.1**, приложение **2026.11.03-max7**.
Назначение: перенести действующий мониторинг упоминаний ЖК с компьютера автора на постоянный сервер.
Инициатор и создатель исходного проекта — сотрудник организационно-аналитического департамента; ФИО и должность заполняются в `AUTHORS.md` и акте передачи.

**Основной вариант: Ubuntu 24.04, Python 3.12, systemd.** Docker — отдельная альтернатива в `DOCKER.md`; одновременно оба варианта не запускаются. PostgreSQL и Redis этому проекту не нужны: он использует SQLite.

## 1. Что получить до начала работ

- Этот архив с кодом.
- Отдельный `data.zip`, созданный **после остановки бота** на прежнем компьютере. В поставку кода он не включён. Пока архив не получен и не проверен, перенос истории не завершён.
- Актуальную папку `config/` с прежнего компьютера: там могли измениться объекты, источники, наблюдаемые аккаунты и файл `entities.learned.yaml` с решениями оператора. Сверить с папкой в поставке и использовать согласованную актуальную версию.
- Заполненный файл секретов, переданный по SSH/SFTP. Шаблон — `.env.example`. Не прикладывать заполненный файл к заявке или репозиторию.
- Контакт ответственного от ОАД, ответственного от IT и время переключения.

Исходный комплект не содержит базы `data/`. Её нельзя заменить пустой базой и считать историю перенесённой. В SQLite находятся пользователи, подписки, очередь уведомлений, история публикаций и часть настроек. Настройки, сохранённые через интерфейс, могут переопределять `settings.yaml`.

Не запускайте два экземпляра с одним Telegram-токеном или одной базой. Это создаёт конфликты получения команд и риск повторной доставки.

## 2. Подготовить сервер

Для предварительного планирования: 4 vCPU, 16 ГБ RAM, SSD от 40 ГБ. Это ориентир, а не результат нагрузочного теста. Место уточнить после получения `data.zip`, с учётом модели и резервных копий. Скорость локальной модели обязательно измерить на целевом сервере; CPU может оказаться недостаточно.

Нужны исходящие соединения к VK, Telegram, выбранным сайтам/RSS, MAX и SMTP, если эти каналы используются, а также к источникам установки Python-пакетов и модели. Порты и адреса согласовать с сетевой службой. Для базового запуска входящий доступ нужен только по SSH из разрешённой сети. Порт 8080 и порт Ollama 11434 не публиковать в интернет.

Администратор заранее устанавливает Python 3.12, venv, pip и unzip из доверенных источников. На чистом Ubuntu 24.04:

```bash
sudo apt-get update
sudo apt-get install -y python3.12 python3.12-venv unzip curl
sudo useradd --system --user-group --home-dir /opt/radar --shell /usr/sbin/nologin radar
sudo install -d -o root -g radar -m 0750 /opt/radar /etc/radar
```

Команда создания пользователя предназначена для первой установки. Если `radar` уже существует, проверить его назначение и права.

Распаковать код во временную папку, затем скопировать **содержимое** `baltdom_monitor/` в `/opt/radar/`. В результате должен существовать `/opt/radar/run.py`, а не `/opt/radar/baltdom_monitor/run.py`. Не распаковывать обновления поверх работающего экземпляра.

```bash
sudo chown -R root:radar /opt/radar
sudo chmod -R u=rwX,g=rX,o= /opt/radar
sudo python3.12 -m venv /opt/radar/.venv
sudo /opt/radar/.venv/bin/pip install -r /opt/radar/requirements.lock.txt
sudo /opt/radar/.venv/bin/pip check
sudo install -d -o radar -g radar -m 0700 /opt/radar/data
sudo chown -R radar:radar /opt/radar/config
```

## 3. Перенести данные и настройки

1. Остановить бот и его автозапуск на старом компьютере. Остановить Colab-воркер на время переноса. Убедиться, что процесса бота больше нет.
2. Создать `data.zip` из всей папки `data/`. Сохранить скрытые файлы и файлы SQLite `-wal`/`-shm`, если они присутствуют. Не удалять их вручную перед архивированием. Отдельно скопировать актуальный `config/`.
3. Передать эти файлы по SSH/SFTP в закрытую временную папку администратора. Не оставлять их в общедоступном каталоге.
4. Проверить ZIP (`unzip -t data.zip`), распаковать во временный каталог и проверить структуру. Перенести содержимое папки `data` в `/opt/radar/data/`. В итоге база должна лежать по пути `/opt/radar/data/radar.sqlite3` — без дополнительного уровня `data/data`.
5. Сохранить исходные архивы как контрольную копию. Согласованную актуальную папку `config/` перенести в `/opt/radar/config/`.
6. Выставить владельца и права:

```bash
sudo chown -R radar:radar /opt/radar/data /opt/radar/config
sudo chmod -R u=rwX,g=,o= /opt/radar/data /opt/radar/config
```

До запуска проверить копию базы под учётной записью `radar` (команда не выводит публикации и данные пользователей):

```bash
sudo -u radar /opt/radar/.venv/bin/python - <<'PY'
import sqlite3
p = 'file:/opt/radar/data/radar.sqlite3?mode=ro'
with sqlite3.connect(p, uri=True) as c:
    result = c.execute('PRAGMA quick_check').fetchall()
    ok = result == [('ok',)]
    print('SQLite: OK' if ok else 'SQLite: проверка не пройдена')
    raise SystemExit(0 if ok else 1)
PY
```

При ошибке остановить перенос и запросить новую согласованную копию. Не «чинить» единственный экземпляр базы на месте. Если уже был использован прежний Docker-вариант с именованным томом, данные нужно экспортировать из того тома: новая поставка использует обычную папку `data/`.

## 4. Передать секреты

Подробный порядок — в `SECRETS_SSH.md`. Конечный путь для systemd: **`/etc/radar/radar.env`**, владелец `root:radar`, права `0640`. Служба читает его через `RADAR_ENV_FILE`; файл `.env` рядом с кодом ей не нужен.

Минимум проверить:

| Параметр | Что указать |
|---|---|
| `GUI_PASSWORD` | Новый случайный пароль, не короче 16 символов |
| `VK_SERVICE_TOKEN` | Рабочий сервисный ключ для используемых методов VK |
| `TG_BOT_TOKEN` | Токен действующего бота |
| `TG_ADMINS` | Числовые ID администраторов; сверить доступ и с перенесённой базой |
| `BRIDGE_TOKEN` | Случайный токен от 32 символов, если используется Colab |
| `MAX_BOT_TOKEN`, `MAX_ADMIN_CHAT_ID` | Только если используется MAX |
| `SMTP_*` | Параметры рабочего почтового ящика, если используется почта |

На постоянном сервере `TUNNEL` обычно оставить пустым. `RELAY_URL` переносить только если релей нужен в новой сети. `RELAY_VIA_COLAB=0` — безопасное начальное значение; при `1` доверенный Colab получает токен Telegram для доставки. Почтовые получатели задаются отдельно в настройках/подписках, одного SMTP-пароля недостаточно.

Не выполнять `source radar.env`: это файл настроек приложения, а не shell-скрипт. Значения записывать одной строкой без `export`, подстановок `$VAR` и комментариев после значения. Для `RADAR_DATA_DIR`, `HOST` и `NICEGUI_STORAGE_PATH` используются параметры службы; не переносить старые пути Windows в них.

## 5. Подготовить нейросеть

Установить Ollama по принятому в IT порядку и запустить её локальную службу. Сверить имя модели с `brain.local.model` в `config/settings.yaml` и, после переноса, с настройками в интерфейсе. В исходной конфигурации:

```bash
ollama pull hf.co/google/gemma-4-E4B-it-qat-q4_0-gguf
ollama list
```

Доступность этой модели и её производительность в текущей среде подготовки не проверялись. Если загрузка не удалась, согласовать доступную модель с ответственным от ОАД и изменить настройку явно. Не считать наличие работающего процесса Ollama подтверждением, что нужная модель загружена.

Бот может продолжать работу по правилам без ИИ. Это резервный режим, а не успешная приёмка нейросетевого анализа. Colab — дополнительный воркер; основной круглосуточный анализ должен быть проверен без него.

## 6. Проверить конфигурацию и запустить

```bash
sudo -u radar env RADAR_ENV_FILE=/etc/radar/radar.env RADAR_DATA_DIR=/opt/radar/data \
  /opt/radar/.venv/bin/python /opt/radar/tools/preflight.py
sudo install -m 0644 /opt/radar/deploy/radar.service /etc/systemd/system/radar.service
sudo systemctl daemon-reload
sudo systemctl enable --now radar
sudo systemctl status radar --no-pager
curl --fail --silent http://127.0.0.1:8080/health
sudo journalctl -u radar -n 80 --no-pager
```

`preflight.py` проверяет конфигурацию без сетевых запросов и не показывает секреты. Ошибки блокируют старт. Если он сообщает о `network.gui_public=true`, сохранить резервную копию и исправить настройку также в перенесённой БД, если она была сохранена там; одного изменения YAML может быть недостаточно.

Для веб-интерфейса выполнить на своём компьютере, подставив SSH-логин и сервер:

```bash
ssh -N -L 18080:127.0.0.1:8080 ituser@server
```

Открыть `http://127.0.0.1:18080`, ввести `GUI_PASSWORD`. SSH-окно оставить открытым. Для постоянного доступа нескольких сотрудников IT может настроить корпоративный VPN/HTTPS отдельно. Не включать публичный GUI ради обхода ошибки 403.

Colab и MAX в режиме polling не требуют одного и того же сетевого решения: MAX polling работает исходящими запросами, а Colab должен иметь доступ к API сервера. Если Colab нужен, настроить домен, HTTPS и Caddy по `deploy/Caddyfile`; снаружи открываются только `/api/brain/*`, `/health` и точный путь `/api/max/webhook`. Веб-интерфейс остаётся закрытым. `/health` не защищён токеном и показывает краткий технический статус. В Colab задать `RADAR_URL=https://ваш-домен` и `RADAR_TOKEN`, равный `BRIDGE_TOKEN`. Старый `vps_setup.sh` предназначен для схемы с ноутбуком и обратным туннелем; для этой установки его не запускать.

## 7. Приёмка вместе с ОАД

- Проверить историю, количество пользователей, подписки, справочники и настройки после переноса.
- Отправить `/status` и `/test` действующему Telegram-боту. `/test` отправляет тестовое уведомление; заранее предупредить получателей. Проверить MAX и почту, если они используются.
- Проверить свежие результаты сборов, состояние источников и очередь анализа; одного `{"ok":true}` от `/health` недостаточно.
- В интерфейсе убедиться, что локальная модель доступна. Без работающей службы можно выполнить `run.py --brain-test` с теми же `RADAR_ENV_FILE` и `RADAR_DATA_DIR`; **сначала остановить службу**, после проверки включить её снова. Эта команда использует настройки проекта и проверяет модель на эталонных текстах.
- Вместе с владельцем методики разобрать расхождения из `VERIFICATION.md`: 12 исходных тестов не проходят. Проверить «наш дом», «чужой корпус», повтор публикации и ручное решение «Наше». Зафиксировать принятое поведение, затем согласовать изменения правил или тестов. Не отмечать эти пункты как пройденные заранее.
- Проверить перезапуск службы, а затем автозапуск после перезагрузки сервера в согласованное окно. Старый экземпляр оставить выключенным.
- Выполнить резервное копирование и пробное восстановление в изолированную папку. Подписать акт с результатами и замечаниями.

До закрытия расхождений запуск считать контролируемой эксплуатацией с ручной проверкой приоритетов, а не полностью принятой промышленной системой.

## 8. Повседневная работа и откат

```bash
sudo systemctl restart radar
sudo systemctl stop radar
sudo systemctl start radar
sudo journalctl -u radar -f
sudo bash /opt/radar/deploy/backup.sh
```

Копирование ненадолго останавливает службу и возвращает её в работу, если она работала до копирования. Архив содержит `data/`, `config/` и номер поставки; секреты хранятся отдельно. Автоматически старые копии не удаляются. IT назначает расписание, срок хранения, контроль свободного места и защищённую копию вне сервера. Встроенные копии SQLite в `data/backups` не заменяют эту процедуру.

Для отката остановить службу. Сохранить неудачное состояние отдельно. Восстановить согласованную пару **код + data/config** из предшествующей резервной копии; файл секретов восстановить отдельно при необходимости. Не смешивать старую БД с `-wal`/`-shm` от другой копии и не запускать старый код поверх уже изменённой базы без проверки. После отката повторить приёмку доставки. Возврат на старый компьютер возможен только при выключенном серверном экземпляре.

`Restart=on-failure` восстанавливает службу после аварийного выхода, но не после намеренного выключения через интерфейс. Статус и свежесть данных должен контролировать внешний мониторинг IT. Необязательный `radar-watchdog.sh` проверяет живость и heartbeat, но не полноту сбора; автоматически в cron он не устанавливается.
